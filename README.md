# Flame in Freefall

Эмулятор пламени в микрогравитации (1D сфера, 2D осесимметричная свеча в потоке, 3D свеча) и суррогатная ML-модель на его данных. 

## Структура

- `emulator/reference/` — 1D сферическое ядро уровня 1 (Python + numba), основной предмет проекта по ТЗ
- `emulator/src/` — то же ядро уровня 1 на C++17 (модуль `_ffcore`, pybind11), побитово сверено с Python-эталоном
- `level2/` — 2D осесимметричное ядро уровня 2: свеча в потоке, параметр гравитации g, метод проекции давления
- `level3/` — 3D декартово ядро (вне ТЗ, по решению в процессе работы): та же физика, что уровень 2, без осевой симметрии
- `emulator/common/` — общее между уровнями: прогонка Томаса, неявная диффузия по линии, обобщённый upwind-градиент, запись истории в HDF5
- `level0_2d/` — прежний 2D плоский решатель, используется как полигон для датчиков/конвейера, физически не развивается
- `formulas/` — безразмерные числа, излучение, кинетика
- `configs/` — YAML-конфиги режимов (`sflame_*` — уровень 1, `candle_l2_*` — уровень 2, `candle_l3_*` — уровень 3)
- `app/` — интерактивное демо на Streamlit (выбор уровня размерности + конфига)
- `tests/` — верификационные и смоук-тесты

## Запуск

```
make build
make test
make app
```

Запуск одного прогона из командной строки с сохранением истории в HDF5:

```
python -m emulator.run configs/sflame_ch4.yaml --out data/run_0001.h5
python -m level2.run configs/candle_l2_base.yaml --out data/run_l2.h5
python -m level3.run configs/candle_l3_base.yaml --out data/run_l3.h5
```

## Статус

**Уровень 1 (1D, сфера):** сферическая геометрия, переменная плотность, стефановский поток, одна глобальная реакция Аррениуса, оптически тонкое излучение, неявная диффузия (метод Томаса) с линеаризованным радиационным стоком — шаг по времени ограничен только числом Куранта по адвекции, не диффузией. Полный прогон (`configs/sflame_ch4.yaml`) укладывается в доли секунды, с большим запасом относительно требования ТЗ «≤2 мин на прогон». Есть два равнозначных backend'а с одинаковым интерфейсом (`step/run/state/qoi`): Python+numba (`emulator.reference`) и C++17 (`emulator._ffcore`, собирается через `make build-l1`) — поля `T/Yf/Yo/rho` после 200 шагов совпадают с точностью `<1e-6` (`tests/test_emu_cpp_vs_reference.py`). C++-версия на сетке 150 ячеек быстрее numba-версии в ~35 раз за счёт отсутствия Python-накладных расходов и явного, непрерывного layout памяти (по одному `std::vector<double>` на поле, без аллокаций внутри шага кроме временных буферов).

**Уровень 2 (2D, свеча в потоке):** осесимметричное низкоскоростное течение в приближении Буссинеска (несжимаемая проекция давления с плавучестью от отклонения плотности, не полный переменно-плотностный low-Mach), горелка-свеча на нижней границе (Dirichlet по температуре/доле топлива на пятне горелки, остальная нижняя граница — стенка), параметр гравитации `g_frac` (0…1) и внешний поток `U_ext`. Давление решается один раз факторизованной разреженной матрицей Лапласа (scipy), каждый шаг — только обратная подстановка. Число Дамкёлера (`formulas.damkohler`) впервые используется по назначению — отличает кинетический срыв от радиационного там, где уровень 1 не мог (не было параметра растяжения). MVP зажигается постоянным пилотным поджигом (игнитер держит `T` в небольшом объёме у горелки всё время прогона) — самостоятельная стабилизация пламени после отключения поджига при этих параметрах погасает за десятки мс и является известным открытым вопросом калибровки, а не багом решателя (сам решатель проверен: `∥∇·u∥ ~ 1e-14` после проекции).

**Уровень 3 (3D, свеча):** прямое обобщение уровня 2 на декартову сетку без осевой симметрии — тот же метод проекции, та же химия/излучение. Позволяет смещать горелку от центра домена (`wick_x0`/`wick_y0`), демонстрируя несимметричные режимы, которые уровень 2 принципиально не может представить.

Общие упрощения уровней 2–3 относительно уровня 1 ТЗ: 2-шаговая химия, 6 компонент, Cantera-калибровка, RADCAL, адаптивная сетка — не сделаны (как и для уровня 1).

## Планы

C++-ядро уровня 1 с явным контролем памяти — сделано (`emulator/src/`, см. выше), как промежуточный этап перед CUDA-ядром. Дальше по плану: то же самое (C++, затем CUDA) для уровней 2–3 — там память уже сейчас организована с прицелом на перенос (матрица давления собирается один раз, явные плотные буферы полей без промежуточных Python-объектов на каждый шаг).
